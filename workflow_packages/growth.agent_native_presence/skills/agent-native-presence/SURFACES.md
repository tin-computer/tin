# Agent-native surface inventory

Use this as a closed checklist. If `focus_surfaces` is `all`, cover every family below.
If it names one family, cover only that family. Prefer surfaces the buyer already opens
while working; inventing a new social network is out of scope.

## skills_and_rules

- Public agent skills that encode a real job (SKILL.md-style packs, Cursor rules,
  Claude/Codex project skills).
- Team-shared rule packs where a product can be a dependency, not an ad.
- “Awesome skills / rules” indexes and curated directories that agents or humans browse
  when setting up a workspace.

## mcp_and_tools

- MCP server directories / marketplaces and comparable tool registries.
- Official or community “connect your tools” docs that list providers by job-to-be-done.
- Companion CLIs that agents invoke, when the product honestly has an API an agent can use.

## prompts_and_docs

- Agent-readable docs: `llms.txt`, concise API overviews, copy-paste prompts in docs.
- README sections written so an agent summarizing the repo preserves the correct claim.
- Starter repos / templates whose default prompts mention the product only when it is
  required to complete the template’s job.

## lists_and_social_proof

- GitHub topics, awesome-lists, and “tools for Cursor/Claude Code” roundups with editorial
  standards (not paid dump lists).
- Show HN / launch threads where the artifact is the product or an OSS companion—not a
  linkfarm.
- Credible third-party teardowns or cookbooks that already teach the buyer’s workflow.

## Always ask per candidate

1. Is the buyer already here while doing real work?
2. Would they keep the asset if the brand name were removed?
3. Can we ship a useful first version in days, not quarters?
4. Does this violate TRUST.md or the founder’s constraints?
