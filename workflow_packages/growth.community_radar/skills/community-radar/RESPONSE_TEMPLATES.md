# Value-First Response Framework & Templates

Every draft generated by `growth.community_radar` must follow the **3-Part Value Framework**. The response must provide genuine standalone value even if the reader never clicks or buys.

---

## The 3-Part Value Framework

1. **Part 1: The Direct Technical Solution (60% of content)**
   - Answer the author's question directly.
   - Provide concrete architecture patterns, command line examples, code snippets, or configuration fixes.
   - Address the root cause of the friction.

2. **Part 2: Objective Trade-Offs & Alternatives (25% of content)**
   - Mention at least one other pattern, open-source tool, or industry standard.
   - Explain the pros and cons objectively. This builds immediate credibility as an expert rather than a commissioned salesperson.

3. **Part 3: Transparent, Low-Pressure Tool Mention (15% of content)**
   - Disclose affiliation clearly: *"Disclosure: I'm the creator of / work on [Product]."*
   - State exactly how the product solves the specific edge case discussed.
   - Keep the call-to-action low pressure: *"Happy to share our config"*, *"Feel free to ping me if you hit any roadblocks"*, or *"Documented here if you want to inspect how it works"*.

## Platform-Specific Draft Templates

### Template 1: Reddit Tool Alternative Request (`r/devops`, `r/SaaS`, `r/webdev`)

```markdown
If you are trying to solve [Problem] without the overhead of [Competitor], the main architectural challenge is [Core Technical Constraint].

Two common patterns work well here:
1. **[Pattern A / Open Source approach]**: You can set up [Tool X] with [Configuration Y]. It gives you full control, but you have to manage [Maintenance burden].
2. **[Pattern B / Dedicated approach]**: If you want something managed with minimal operational overhead, look into [Competitor B] or [Product].

*Disclosure: I'm on the team building [Product].* We built it specifically because we ran into the exact same [Pain Point] with [Competitor]. We [Brief explanation of 1 key technical differentiator, e.g., 'store data directly in your S3 bucket so you avoid per-gigabyte indexing fees'].

Happy to answer any questions about our [relevant technical detail] if you're exploring this path.
```

### Template 2: Hacker News Technical Breakdown (`Ask HN` or Discussion)

```markdown
The reason [Competitor / Existing pattern] breaks down at scale for [Problem] is [Technical root cause, e.g., connection exhaustion / memory pressure during compaction].

If you're building this in-house, the standard mitigation is to [Concrete engineering recommendation, e.g., introduce a write-ahead log buffer using Redis Streams].

For off-the-shelf options:
- [Open Source Tool A] is solid if you're already running Kubernetes and don't mind managing Helm charts.
- [Cloud Service B] works out of the box, but their billing scales linearly with event volume.

Full disclosure: I'm one of the authors of [Product]. We tackled this by [Architecture explanation, e.g., decoupling ingestion from querying using DuckDB/Parquet]. It's open-source / documented at [Link], and the design doc on [Technical topic] might be useful regardless of which tool you end up choosing.
```

## Banned Phrasing & Antipatterns

Never include these marketing tropes in any draft:
- ❌ *"Revolutionary / Game-changing / Next-generation"*
- ❌ *"Let's jump on a quick 15-minute call"*
- ❌ *"Our all-in-one platform does it all"*
- ❌ *"Check out our website: [sales page link with UTM tracking]"*
- ❌ *"Why build it when you can just buy [Product]?"*
- ❌ Fake enthusiasm (*"Awesome post! Wow, totally agree!"*)
- ❌ Unsolicited DMs when the poster did not ask for them.
